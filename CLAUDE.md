# Siła z Ruchu – aplikacja dla klientów Damiana (repozytorium `trening`)

Aplikacja, w której klienci trenera personalnego (ciężary, siła, sylwetka) widzą plan i zapisują wykonanie: serie, RPE, filmy, ból i samopoczucie. Dane trafiają do Arkusza Google Damiana, filmy na jego Google Drive. Arkusz liczy tygodniowe podsumowanie obciążenia ze statusem (za dużo / uwaga / OK / za lekko).

Marka od 17.11.2026 to „Siła z Ruchu”: tę nazwę widzi klient (pod ikoną na ekranie głównym, w karcie przeglądarki, w nagłówku przed wczytaniem planu, w animacji otwarcia). „Trening” zostaje jako nazwa repozytorium i adresu strony, arkusza, folderów Drive („Trening – Klienci”), pliku podglądu, menu arkusza, tematu alertu mailowego, panelu trenera (`web/trener.html`, widzi go tylko trener) i ekranu w dolnym menu. Nie zmieniaj ich: nazwa folderu jest w kodzie (`ROOT_FOLDER_NAME`) i w skillu trenera, a adres strony jest w linkach klientów.

Rozmawiaj z Damianem po polsku, zwięźle. Interfejs aplikacji jest po polsku.
Zasady pracy (PR dopiero po zgodzie Damiana, oznaczanie zadań w md od razu, tłumaczenie testów) są w `docs/stan.md`, „Jak pracujemy”.

## Architektura

```
web/  (PWA, GitHub Pages)  ──fetch POST text/plain──▶  apps-script/Code.gs (web app /exec, doPost)
  index.html                                           │
  config.js  (API_URL)                                  ├─▶ Arkusz: Plan, Klienci, Log, Sesje, Import, Podsumowanie*
  sw.js      (offline)                                  └─▶ Drive: „Trening – Klienci/<Imię>/<data>_<jednostka>/” (filmy)
  manifest.json, icons/                                       „Trening – Klienci/_plany/” (plany JSON → wczytajPlany)
Filmy: telefon → Drive bezpośrednio (sesja resumable otwierana przez startUpload z nagłówkiem Origin),
       awaryjnie przez serwer w kawałkach 4 MB (uploadChunk).
```

- `web/index.html` to jeden plik (HTML + CSS + JS), bez bundlera i frameworka; czyste funkcje (bez DOM) są w `web/lib.js` (`window.TL`, testy `tests/lib.test.js`), czcionki w `web/fonts/`. Cała komunikacja z serwerem idzie przez funkcję `call(fn, ...args)`.
- `apps-script/Code.gs` (oraz `Trener.gs`, `Podglad.gs`, `Cwiczenia.gs`) jest powiązany z arkuszem `Trening – Aplikacja (dane)` (konto trenera, właściciel arkusza; `clasp login` musi być na tym samym koncie). API: `doPost` → `API_FNS` (getData, logSet, logSession, deleteSet, startUpload, uploadChunk, uploadStatus, logVideo, saveDyspozycja, przesunJednostke, addOwnUnit, getExNames, logError, logNote, logReadyVideo, editPlan). Pierwszym argumentem każdej funkcji jest klucz klienta.
- Stara wersja (`apps-script/Index.html`, `doGet` + `google.script.run`, linki `/exec?k=`) usunięta 17.11.2026. `doGet` zwraca tylko zwykły tekst „wersja wyłączona” (`ContentService`, `oldLinkText_`). **Nie wracaj do stron `HtmlService` w `doGet`**: z każdej publicznej strony HtmlService da się przez `google.script.run` wywołać każdą funkcję bez „_” na końcu (np. `dodajKlientaZapisz`), także bez klucza. Okna w arkuszu (Dodaj klienta) są w porządku, bo otwiera je tylko trener.
- Klucz klienta w linku (`?k=k` + 11 znaków hex) jest jedynym zabezpieczeniem. PWA zapamiętuje go w `localStorage` („key”). Bez klucza (iOS: PWA z ekranu głównego ma osobny `localStorage` i startuje bez `?k=`) `askKey` pokazuje pole na link albo kod (lib `keyFrom`).
- Nowe zapisy to nowe akcje w `API_FNS` wywoływane przez `call()` (np. `saveDyspozycja`), nigdy `google.script.run`.

## Polecenia

```bash
npm test                         # testy Node (Code.gs w piaskownicy, web/lib.js) + UI w Playwright z atrapą API; zrzuty w tests/screens/
npm run test:code                # tylko logika serwera
node tools/validate-plan.js plans/x.json   # sprawdzenie planu przed wrzuceniem na Drive
node tools/make-icons.js                   # ikony w web/icons/ rysowane z toru animacji otwarcia (po zmianie podbij VERSION)
npm run serve                    # podgląd web/ na http://localhost:8080 (API z config.js)
npm run gas:push                 # clasp push → Apps Script (pliki z apps-script/)
DEPLOYMENT_ID=… npm run gas:deploy   # nowa wersja istniejącego wdrożenia (URL /exec bez zmian)
git push                         # zmiany w web/ → GitHub Actions → GitHub Pages
```

Każda zmiana w `web/` wymaga podbicia `VERSION` w `web/sw.js`, bo inaczej telefony mogą trzymać starą wersję.
Każda zmiana w `Code.gs` wymaga `gas:push` i `gas:deploy`. Bez deploy telefon dalej rozmawia ze starą wersją API.
Robi to automatycznie `.github/workflows/apps-script.yml` po scaleniu zmian w `apps-script/**` do `main` (testy → `clasp push` → nowa wersja istniejącego wdrożenia). Sekrety repozytorium: `CLASPRC_JSON`, `SCRIPT_ID`, `DEPLOYMENT_ID`. `clasp push` zastępuje cały projekt Apps Script plikami z `apps-script/`, więc poprawki zrobione tylko w edytorze Apps Script przepadną: najpierw przenieś je do repo.

## Dane (arkusz)

**Plan** (PLAN_HEADERS w Code.gs): klient, tydzien, jednostka, tytul, data (RRRR-MM-DD, tekst; opcjonalna = wstępna, klient może przesunąć), nr, cwiczenie, prio (A/B/K), serie, powt (tekst: „8”, „6-8”, „8/str”, „1+1”), procent (ułamek), kg (liczba lub tekst: BW, guma), rpe_max, uwagi, dod_serie, drop, grupa (R/P/CR/CP/PS/I), zamienniki („;”), blok (np. B2), zrodlo (klient = własny trening; dodane / usuniete / usuniete_d = zmiany klienta w jednostce trenera), tryb (EMOM), ciecie (1 = tnij pierwsze), serie_min, obwod (litera A–Z: sąsiednie ćwiczenia jednostki na zmianę, min. 2, bez EMOM; `circuit_`, w getData `row.circuit`), uwagi_jedn (notatka trenera do całej jednostki, w jednym wierszu jednostki; dwie różne w jednostce = błąd walidacji; w getData `row.unote`, w aplikacji karta „Od trenera” `#unote` nad kartą „dziś”, `unoteCard`; w trybie skupienia tylko na pierwszym kroku). Serie 1–40 (`SETS_MAX`).
Kolumny E (data), J (powt) i L (kg) muszą mieć format `@` ustawiony PRZED zapisem, bo inaczej Arkusze zamienią „6-8” w datę.
Tygodnie u klienta numeruj **ciągle** między blokami (blok 2 od tyg. 7): id serii nie zawiera bloku, więc powtórzony numer tygodnia nadpisałby Log.

**Klienci**: A klucz, B klient_id, C imie, D aktywny (TAK/NIE), E link, F bol (TAK), G tryb (PROSTY/PRO), H dod_serie, I masters (TAK), J zamiana (NIE / TRENER / DOWOLNA; TAK = TRENER, `swapMode_`), K skala (RPE/RIR), L sufit_oly (ułamek lub %, domyślnie 0,05), M wlasne (NIE wyłącza własne treningi), N edycja (TAK = zmiany w jednostce trenera). `getData` zwraca je w `cfg` jako `swap` ('TRENER' | 'DOWOLNA' | false), `scale`, `olyCeil`.

**Log**: id = klient|tydzien|jednostka|nr|seria (upsert), zapisano, klient, tydzien, jednostka, data, nr_cw, cwiczenie, seria, kg, powt, rpe, vbt_ms, wykonane, film_link, uwagi, typ, ocena (L/S/W/X), vbt_peak, wysokosc_cm, sciezka (JSON), zamiana („oryginał → zamiennik | powód”).
Wartości `seria`: 1…n robocze, n+1… dodatkowe, R1… rozgrzewka, D1… drop set, 0 = ćwiczenie pominięte/skrócone. Wartości `typ`: DROP / FAIL / DROP+FAIL / SKIP (seria 0, `wykonane` puste, powód w `uwagi`: „skrócone do 2 z 4 serii · brak czasu” albo sam powód; `skips_`).
`uwagi` w seriach = komentarz klienta do ćwiczenia (ten sam we wszystkich seriach; `logNote` poprawia wszystkie).
`logSet` przyjmuje pola v2: `ocena`, `vbtPeak`, `height`, `path`, `swap` (brak = puste, stara aplikacja działa bez zmian).

**Sesje**: id = klient|tydzien|jednostka, …, samopoczucie (1–5), czas_min, uwagi, start, koniec, bol („miejsce:0–10; …”), bol_max, rpe_sesji (0–10, CR-10).
Kolumna `data` w Sesjach to data z planu; faktyczny dzień treningu to `start` (`unitDates_`) i według niego podsumowanie grupuje tygodnie.

**Dyspozycja**: id = klient|data (jeden wpis dziennie), zapisano, klient, data, cmj1–3, cmj_sr, sen, stres, zmeczenie, bolesnosc, hooper_suma, vbt_test, werdykt, powody, cmj_wykluczone („2”: skok poza `cmj_sr`), film_link (filmy CMJ, `logReadyVideo`, Dysk „<Imię>/Dyspozycja/<data>/”). Zapis: `saveDyspozycja` (krótszy wiersz, nie kasuje film_link); `getData` zwraca `readiness`.

**Ćwiczenia** (baza, startowo z `apps-script/Cwiczenia.gs` przez menu „Wczytaj bazę ćwiczeń”; poprawki trener robi w arkuszu): cwiczenie, aliasy („;”), instruktaz (link http/https), partia (kilka przez „;”), zamienniki („;”), grupa. Dopasowanie nazwy z planu (`exIndex_`, `exFind_`): dokładna nazwa lub alias → nazwa podstawowa (bez nawiasów, „– TEST”, „z pauzą…”) → te same słowa i skróty (DB, SL, RDL); bez zgadywania po podobieństwie. Kompleks „A + B” bez własnego wiersza składa się z części (`exInfo_`). `getData` dokłada do wierszy planu `infos` [{n, u}] i `parts` [], domyślne `swaps` i `group` (plan ma pierwszeństwo) oraz mapę `parts` {nazwa → [partie]} dla nazw z planu, logu i zamienników klienta. Menu „Uzupełnij listę ćwiczeń” dopisuje nazwy z Planu bez dopasowania. W `Cwiczenia.gs` są też `CW_FEDB` (762 ćwiczenia z free-exercise-db: nazwa i partia, bez filmu), `CW_WYCOFANE` (błędne aliasy usuwane z arkusza), `CW_ALIASY` (polskie i potoczne nazwy ćwiczeń z bazy) i `CW_DODATKI` (ćwiczenia spoza Catalyst, bez filmu); `cwSync_` (czysta funkcja z testem) wylicza, co „Wczytaj bazę ćwiczeń” ma dopisać, i nie rusza ręcznych wpisów. Wiersz z samą nazwą (zaślepka) nie bierze udziału w dopasowaniu.

**Pominięte i komentarze w podsumowaniu**: Podsumowanie_cw `uwagi_klienta`, `pominiete`; Podsumowanie `opcjonalne` (zrobione/plan B). Pominięte albo skrócone B nie wchodzą do `wykonanie_%` (Podsumowanie i Bloki), A/K tak; pominięte A/K = sygnał pomarańczowy w Przeglądzie.

**Podsumowanie_partie** (`computeParts_`): klient × tydzień × partia: serie, serie twarde (RPE ≥ 7, FAIL, DROP), tonaż; ćwiczenie liczy się do każdej swojej partii; po zamianie liczy się wykonane ćwiczenie. Boje olimpijskie i ich warianty nie mają partii w bazie.

**Przegląd** (liczony w `podsumowanie`, `computeOverview_`): jeden wiersz na aktywnego klienta, najpilniejsi na górze; `pilnosc` = 3 × sygnały czerwone + pomarańczowe (ból > 3/10, FAIL, dyspozycja, zaległe jednostki, brak treningu, koniec planu), ostatni trening, ten tydzień zrobione/plan, uwagi klienta, filmy z 7 dni, filmy z 7 dni bez komentarza trenera (`filmy_bez_kom_7dni`, bez sygnału). Progi i okna: stała `PRZ` i `docs/plan-v3.md`.

**Niezawodność**: `cwRowsCached_` (Ćwiczenia w CacheService w kawałkach, `cwCacheClear_`, prosty wyzwalacz `onEdit`), `getData.ms` (czasy etapów), `ownWrite_` (własny trening bez przepisywania Planu), zakładka Błędy (`logError`, `errRow_`, `errRecent_`; w aplikacji `reportErr`, limit 5 dziennie).

**Własny trening klienta** (`addOwnUnit`, `ownRows_`, `ownRecent_`; aplikacja `openOwn` / `applyOwn`, lib `ownWeek`, `ownNextDay`, `exSearch`): jednostki W1, W2… z `Plan.zrodlo = klient`; `own_(r)` wyłącza je z wykonania planu (computeSummary_, computeBlocks_, computeOverview_) i chroni przy `mergePlan_`. `getData` zwraca `row.own` i `cfg.own` (Klienci M „wlasne”); `getExNames` zwraca do wyszukiwarki `[nazwa, link do filmu albo '', partie „a; b”]` (telefon: `exn2_<klucz>`, doba), z czego `applyOwn` od razu dokłada „Jak wykonać” i partie, a `ownParts` robi filtr po partii mięśniowej (lib `exParts`, `exSearch(…, part)`). Kompleks w kreatorze: „⛓ Połącz z poprzednim” → Kompleks / „Rozłącz” (lib `isComplex`, `ownJoin`, `ownSplit`, `complexRepsOk`) daje jedno ćwiczenie „A + B” z powt. „1+2”, bez zmian w arkuszu. Ćwiczenie na czas: `powt` = „30 s” (przycisk „⏱ na czas” w `ownList`; lib `timeUnit`, `repsLabel`): w wierszu serii „sek.” zamiast „powt.”, sekundy w `Log.powt`, bez tonażu w aplikacji i w arkuszu (`timed_` w Code.gs wg `Plan.powt`: bez tonażu, e1RM i NL, serie liczone). Ćwiczenia: kolumna `glowna` = alias ćwiczenia głównego (`exIndex_` drugi przebieg, `cwMerge_` przenosi do aliasów).

**Zmiany klienta w jednostce trenera** (Klienci N `edycja` = TAK → `cfg.edit`; API `editPlan`, czysta `planEdit_`; aplikacja `EDIT`, `openAdd`, `openDel`, `edRemoved` / `edUndel`, `lenSeg` / `bindLen`, `applyEdit` / `edSend`, lib `planEdit` z tą samą regułą): `Plan.zrodlo` = `dodane` (ćwiczenie dopisane, `nr` od 51, `EDIT_NR`), `usuniete` (ćwiczenie z planu usunięte, wiersz zostaje jako ślad), `usuniete_d` (usunięte dodane). „Na stałe” = także kolejne tygodnie tej samej jednostki w tym samym bloku, niezrobione, po nazwie ćwiczenia; zamiana na stałe zmienia `cwiczenie` w kolejnych tygodniach i dopisuje do `uwagi` „zamiana klienta: A → B” (bieżąca jednostka dalej przez Log `zamiana`). `offPlan_(r)` (własne, dodane, usunięte) wyłącza wiersz z wykonania planu, jednostek i zaległych; serie liczą się do objętości. `getData` nie zwraca usuniętych w `plan`, tylko w `removed` [{week, day, order, name}], dodane mają `row.added`. `mergePlan_` zachowuje zmiany w niezrobionych jednostkach (Import: „zachowano n zmian klienta”). W telefonie zmiana trafia do pamięci `d_<klucz>` dopiero po potwierdzeniu serwera; do tego czasu żyje w kolejce i `useData` nanosi ją raz.

**Kolejka filmów** (web/index.html, `queueVideo` / `vqRun` / `vqOne`): plik w IndexedDB `trening-filmy`, postęp sesji w localStorage `vqp_<id>`; wysyłka kawałkami po 8 MB na sesję resumable z `startUpload` (z Origin), awaryjnie cały plik naraz, a potem przez serwer (`uploadChunk`). Wznowienie pyta `uploadStatus` (serwer odczytuje Range, bo przeglądarka go nie widzi), link przy serii zapisuje `logVideo` (tylko film_link). Test UI symuluje przerwę i wznowienie po przeładowaniu.

**Komentarze trenera**: `Log.komentarz_dysk` wypełnia skrypt z komentarzy do filmu na Dysku (`syncComments_` przez Drive REST; `commentLines_`, `anchorSec_`, `fileIdOf_` to czyste funkcje z testami; wołane z `wczytajPlany(e)` nie częściej niż co 30 min i z menu), `komentarz_trenera` w Logu i Sesjach wpisuje trener ręcznie. Nowe kolumny są na końcu nagłówków, a `logSet` / `logSession` zapisują krótsze wiersze, więc ponowny zapis serii przez klienta nie kasuje komentarza: nie wstawiaj kolumn w środek. Aplikacja: `coachNotes` i `notesByWeek` w lib.js, karta `notesCard` z nowymi na Treningu, wszystkie w zakładce Trener (`renderTrener`, tygodniami i jednostkami, „NOWE” do wyjścia z zakładki, kropka na przycisku w menu, `navDot`), przeczytane w localStorage `cn_<klucz>`. Klient nie widzi, które filmy czekają na komentarz (to tylko w Przeglądzie).

**Alert mailowy** (`alertMail_`, czysta funkcja z testem; `alertRano_`): wysyłany tylko z porannego wyzwalacza `podsumowanie(e)` (z menu nie), na adres z właściwości skryptu `ALERT_EMAIL` (menu „Ustaw adres alertu”; adresu nie wpisuj do repo ani arkusza). Mail idzie tylko, gdy pojawił się czerwony sygnał, którego nie było w poprzednim alercie (podpis w `ALERT_SIG`); liczba czerwonych sygnałów klienta jest w kolumnie `czerwone` Przeglądu. `MailApp` wymaga zgody właściciela arkusza: po wdrożeniu zmiany dodającej nowy zakres uprawnień trzeba od razu uruchomić dowolną pozycję menu i zaakceptować zgodę, inaczej aplikacja klientów przestaje zapisywać.

**Podgląd dla Claude** (`apps-script/Podglad.gs`; `podglad_` czysta funkcja z testem): osobny plik „Trening – podgląd dla Claude” w folderze „Trening – Klienci”, jedna zakładka „Ostatnie sesje”: 5 ostatnich jednostek każdej osoby (aktywni klienci i trener, który zapisuje się jak klient; nieaktywni pominięci), osoby alfabetycznie po imieniu z Klientów, w obrębie osoby od najnowszej (dzień z Sesje.start, inaczej z Logu), wiersz „— sesja —” (RPE sesji, samopoczucie, czas, uwagi) + wiersz na ćwiczenie (plan kg / serie×powt. / RPE, wykonanie bez rozgrzewki, notatki: komentarz klienta, zamiana, pominięcie, uwagi z planu). Bez bólu i komentarzy trenera. Dla agenta z konektorem Drive, który nie czyta dużego arkusza. Odświeża `odswiezPodglad` z wyzwalacza co 10 min (`instalujPodglad`, raz z edytora), przepisuje plik tylko po zmianie (`PODGLAD_SIG`); ID pliku we właściwości `PODGLAD_ID`. Log czyta bez kolumny `sciezka` (`pgTable_`). Nie zmienia żadnej zakładki arkusza z danymi.

**Bloki** (liczone w `podsumowanie`, `computeBlocks_`): klient × blok, daty, tygodnie, jednostki, wykonanie, tonaż, zmiana e1RM, najlepsze boje, sRPE, samopoczucie, dyspozycja, ból, statusy, **wnioski** (wpisuje trener, tylko dla niego), **dla_klienta** (wpisuje trener, klient widzi w raporcie po bloku; `blockNotes_` → `getData.blockNotes` {blok → tekst}); `keepNotes_` zachowuje obie kolumny (`BLOK_NOTES`) przy przeliczaniu.

**Panel trenera** (`web/trener.html`, `apps-script/Trener.gs`, `docs/plan-panel.md`): strona dla trenera na komputer (działa też na telefonie), nie PWA, bez trybu offline i bez danych klientów w `localStorage` (tylko bilet `tr_tok`). Logowanie Google Identity Services (skrypt `accounts.google.com/gsi/client` ładowany tylko w panelu) → ID token wysyłany jako `token` zamiast `key`; `doPost` kieruje akcje z `TR_FNS` (trConfig, trPulpit, trKlient, trPrzelicz, trKomentarz, trSzkic, trAI, trUstawAI, trFilm, trKomentarzFilm, trBlok, trBlokSzkic) przez `trAuth_` (tokeninfo, `trTokenOk_` czysta funkcja z testem, CacheService do 1 h), a akcje klientów z `API_FNS` dalej po kluczu; nazwy obu list nie mogą się pokrywać. Błąd logowania zaczyna się od „Logowanie: ” (`TR_AUTH`), panel wraca wtedy do logowania. Właściwości skryptu `TRENER_CLIENT_ID` i `TRENER_EMAIL` (menu „Ustaw panel trenera”, `ustawPanel`; nie do repo). `trPulpit_` (czysta, z testem) składa pulpit z Logu (bez `sciezka`), Przeglądu, Podsumowania, Bloków i Klientów; `trKlient` = `clientData_` (wspólne z `getData`) + bloki i podsumowanie klienta. `podsumowanie()` zapisuje czas przeliczenia w `PODSUM_AT`. ## Plany treningowe

Plany tworzy Claude w projekcie claude.ai („Trener personalny (OLY)”) i zapisuje je jako JSON do `Trening – Klienci/_plany/` na Drive.
`wczytajPlany()` działa z wyzwalacza co 15 min albo z menu „Trening”. Menu „Trening” (`onOpen`) ma też: Przegląd klientów, Dodaj klienta, Odśwież linki klientów, Sprawdź arkusz (`diagnose_`, czysta funkcja z testem) i Zainstaluj wyzwalacze; okna w arkuszu mogą używać `google.script.run`, bo to interfejs trenera, a nie `web/`. Kolejno: waliduje plik (`validatePlan_`), podmienia wiersze klientów z pliku (`mergePlan_`: **tylko bloki, które plik zawiera** (`blok`, pusty też jest blokiem) i jednostki z pliku; niezrobione jednostki tych bloków spoza pliku znikają i każda jest w Import „usunięto: klient tydz. X jednostka Y (blok Z)”, status „OK (usunięto N)” (`removed`, `importStatus_`); inne bloki klienta zostają; jednostka zrobiona = wpis w Sesjach **albo** seria w Logu (`wczytajPlany` czyta z Logu trzy kolumny przez `pgTable_`) i zawsze zostaje bez zmian, spoza pliku z uwagą; niezrobiona jednostka innego bloku z tym samym tygodniem i dniem co plik = zastąpiona, uwaga; własne (`zrodlo` = klient) nietknięte; zrobiona jednostka z innym blokiem w pliku = błąd; opcjonalne pole wiersza `zastepuje` = blok, którego niezrobione jednostki klienta z datą ≥ pierwszej daty klienta w pliku są zamykane, bez ruszania Logu, Sesji i własnych; w Import „zamknięto n jedn. bloku X”, nieistniejący blok = uwaga; `zastepuje` nie jest kolumną Planu), przenosi plik do `_plany/wczytane` albo `_plany/bledy` i zapisuje wynik w zakładce Import.
Konwencje Damiana:
- % z max;
- kg zaokrąglane **w dół** do 2,5 kg;
- rpe_max to sufit;
- ćwiczenia korekcyjne mają prio K;
- boje mają dod_serie = 0;
- u ciężarowców procent wpisany przy każdym ćwiczeniu specjalnym.

## Interfejs (web/index.html)

- `Index.html` jest wspólny dla wszystkich klientów. Różnice między klientami robi się przez `cfg` z getData (pain, simple, extra) albo przez kolumny planu, **nigdy** przez warunki na konkretne imię.
- Tryb prosty (`SIMPLE`):
  - „jak ciężko?”: te same światła co w PRO (Lekko / Średnio / Ciężko / Nieudana), słowem zamiast liczby, bez dokładnego RPE;
  - „✓ Wszystko jak w planie”;
  - podpowiedź RIR;
  - ukryte VBT i %.
- Pola kg / powt.: propozycja (plan, poprzednia seria, drop) to placeholder (`data-ph`, klasa `ph`), pole puste; wartość czytaj przez `fv(input)`, nową propozycję ustawiaj `setPh`. ✓ przy pustym polu wpisuje propozycję. Pole z wartością zaznacza się przy fokusie.
- Serie:
  - dodatkowe przyciski „+ rozgrzewka”, „+ seria (N)” i „+ drop set” (~80% ciężaru, w dół do 2,5 kg; „⇣ Jak 1. seria” usunięte w v4);
  - ✕ usuwa ostatni dodany wiersz w dwóch dotknięciach;
  - pole odhaczenia (`data-st`): puste → ✓ zrobiona → ✕ nieudana (typ FAIL, rpe puste) → puste; żółte (`pend`) = czeka w kolejce;
  - dotknięcie numeru serii roboczej/dodatkowej: zwykła → drop (typ DROP) → nieudana;
  - zmiana kg/powt./RPE w zapisanej serii zapisuje ją od razu;
  - **wysiłek serii = światło** (v59, jedna skala w całej aplikacji, lib `EFF`, `lightOf`, `EFF_FINE`): w wierszu przycisk `.ef` („oceń”), dotknięcie → pod wierszem `.efp` z czterema światłami, wybór od razu zapisuje serię (`save(st, oc, rpe)`, RPE w `row.dataset.rpe`):

    | Światło | `rpe` w Logu | `typ` | Podpis |
    |---|---|---|---|
    | 🟢 Lekko | 7 | – | Szybko, czysto, zapas ≥ 3 |
    | 🟡 Średnio | 8 | – | Wolniej albo z poprawką, zapas 2 |
    | 🔴 Ciężko | 9 | – | Walka, zapas 0–1 |
    | ✖ Nieudana | puste | FAIL | Seria nie wyszła |

    Odczyt (też stare wpisy, `lightOf`): ≤ 7,5 → 🟢, 8–8,5 → 🟡, ≥ 9 → 🔴, FAIL → ✖, puste → „oceń”. **Bez wartości domyślnej**: ✓ bez światła zapisuje puste RPE, nigdy 7; „✓ Wszystko jak w planie” nie ustawia światła; rozgrzewka bez świateł; „Bez oceny (zostaje ✓)” czyści RPE. W Logu tylko liczba RPE (+ FAIL); światło to jej widok. PRO: w wierszu liczba RPE albo „RIR n” wg `cfg.scale` i przełącznika w nagłówku (`sc_<klucz>`), w okienku przy zaznaczonym świetle „Dokładniej” z wartościami `EFF_FINE` (zakres światła i krok do sąsiedniego, np. 🟡 7,5 / 8 / 8,5 / 9; przy RIR w RIR), zapis zawsze w RPE; PROSTY: słowo, bez „Dokładniej”. **Puste RPE = brak danych** w arkuszu (`n_` → NaN: bez e1RM, bez RPE względem planu, nie seria twarda); wyjątek tylko w aplikacji: rekord i wykres Siły liczą serię bez RPE jak RPE 10 (`L.e1rm`, ustalenie 17.11);
  - recepta: kwadrat w kolorze talerza wg % 1RM, „RIR ≥ n” przy skali RIR; „Ostatnio: kg × powt. · RPE” z poprzedniej jednostki (`lastTop`) jest przyciskiem (`button.last`, `data-hist`) i otwiera okno „Historia” (`openHist`, lib `exHistory`): wykres siły z `strengthSeries` (ostatnie 5 punktów, rekordy z całej historii) i 5 ostatnich jednostek z tym ćwiczeniem bez bieżącej (serie w skrócie, najlepsza seria, wysiłek przez `effTxt`); jeden trening albo ćwiczenie na czas = bez wykresu.
  - rekord w chwili zapisu (`recDraw`, lib `unitRecord`, serie z `unitSets`): pasek `.rec` „★ Rekord” pod najlepszą zaliczoną serią ćwiczenia głównego (A), gdy bije całą historię sprzed tej jednostki (e1RM, w bojach kg; nie FAIL, nie na czas; pierwszy wynik ćwiczenia bez historii = pasek `.rec.first` „★ Pierwszy wynik” (obrys zamiast wypełnienia, PRO z wartością bez „było”, PROSTY „Od niego liczymy rekordy”, w zwiniętej karcie „★ pierwszy wynik”; `unitRecord` zwraca `first: true`, `unitSummary` go pomija); seria bez RPE liczy się w aplikacji jak RPE 10, `L.e1rm`, arkusz bez zmian); jeden na ćwiczenie, PRO „szacowane maks. X kg · było Y”, PROSTY bez liczb; rysowany przy zapisie serii i w `refreshDel`, bez toastu i dźwięku; zwinięta karta ma w wyniku „★ rekord” (`recSum`);
  - „✓ Wszystko jak w planie” (PROSTY) widoczne tylko przy niezapisanych seriach z planu (`refreshAll`);

  - po zaliczeniu serii (✓/✕, nie rozgrzewka) timer przerwy nad dolnym menu: A 2:00, B 1:30, K 1:00 (`restSec`), −15 / +15 / Pomiń, wibracja na koniec; pasek postępu 8 px na górnej krawędzi, w ostatnich 10 s (`REST_END`) klasa `#rest.end` (czerwone cyfry i pasek, „Zaraz koniec · …”);
