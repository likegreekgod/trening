# Siła z Ruchu – aplikacja dla klientów Damiana (repozytorium `trening`)

Aplikacja, w której klienci trenera personalnego (ciężary, siła, sylwetka) widzą plan i zapisują wykonanie: serie, RPE, filmy, ból i samopoczucie. Dane trafiają do Arkusza Google Damiana, filmy na jego Google Drive. Arkusz liczy tygodniowe podsumowanie obciążenia ze statusem (za dużo / uwaga / OK / za lekko).

Marka od 17.11.2026 to „Siła z Ruchu”: tę nazwę widzi klient (pod ikoną na ekranie głównym, w karcie przeglądarki, w nagłówku przed wczytaniem planu, w animacji otwarcia). „Trening” zostaje jako nazwa repozytorium i adresu strony, arkusza, folderów Drive („Trening – Klienci”), pliku podglądu, menu arkusza, tematu alertu mailowego, panelu trenera (`web/trener.html`, widzi go tylko trener) i ekranu w dolnym menu. Nie zmieniaj ich: nazwa folderu jest w kodzie (`ROOT_FOLDER_NAME`) i w skillu trenera, a adres strony jest w linkach klientów.

Rozmawiaj z Damianem po polsku, zwięźle. Interfejs aplikacji jest po polsku.
Zasady pracy (PR dopiero po zgodzie Damiana, oznaczanie zadań w md od razu, tłumaczenie testów) są w `docs/stan.md`, „Jak pracujemy”.

## Architektura

```
web/  (PWA, GitHub Pages)  ──fetch POST text/plain──▶  apps-script/Code.gs (web app /exec, doPost)
  index.html                                           │
  config.js  (API_URL)                                  ├─▶ Arkusz: Plan, Klienci, Log, Sesje, Import, Podsumowanie*
  sw.js      (offline)                                  └─▶ Drive: „Trening – Klienci/<Imię>/<data>_<jednostka>/” (filmy)
  manifest.json, icons/                                       „Trening – Klienci/_plany/” (plany JSON → wczytajPlany)
Filmy: telefon → Drive bezpośrednio (sesja resumable otwierana przez startUpload z nagłówkiem Origin),
       awaryjnie przez serwer w kawałkach 4 MB (uploadChunk).
```

- `web/index.html` to jeden plik (HTML + CSS + JS), bez bundlera i frameworka; czyste funkcje (bez DOM) są w `web/lib.js` (`window.TL`, testy `tests/lib.test.js`), czcionki w `web/fonts/`. Cała komunikacja z serwerem idzie przez funkcję `call(fn, ...args)`.
- `apps-script/Code.gs` (oraz `Trener.gs`, `Podglad.gs`, `Cwiczenia.gs`, `Mail.gs`, `Kopia.gs`, `Pakiety.gs`, `Import.gs`) jest powiązany z arkuszem `Trening – Aplikacja (dane)` (konto trenera, właściciel arkusza; `clasp login` musi być na tym samym koncie). API: `doPost` → `API_FNS` (getData, logSet, logSession, deleteSet, startUpload, uploadChunk, uploadStatus, logVideo, saveDyspozycja, przesunJednostke, addOwnUnit, getExNames, logError, logNote, logReadyVideo, editPlan, saveStan, deleteStan, replyNote). Pierwszym argumentem każdej funkcji jest klucz klienta.
- Stara wersja (`apps-script/Index.html`, `doGet` + `google.script.run`, linki `/exec?k=`) usunięta 17.11.2026. `doGet` zwraca tylko zwykły tekst „wersja wyłączona” (`ContentService`, `oldLinkText_`). **Nie wracaj do stron `HtmlService` w `doGet`**: z każdej publicznej strony HtmlService da się przez `google.script.run` wywołać każdą funkcję bez „_” na końcu (np. `dodajKlientaZapisz`), także bez klucza. Okna w arkuszu (Dodaj klienta) są w porządku, bo otwiera je tylko trener.
- Klucz klienta w linku (`?k=k` + 11 znaków hex) jest jedynym zabezpieczeniem. PWA zapamiętuje go w `localStorage` („key”) i od v72 usuwa z paska adresu (`history.replaceState`, lib `urlNoKey`; gdy zapis do pamięci się nie udał, klucz zostaje w adresie). Bez klucza (iOS: PWA z ekranu głównego ma osobny `localStorage` i startuje bez `?k=`) `askKey` pokazuje pole na link albo kod (lib `keyFrom`).
- Nowe zapisy to nowe akcje w `API_FNS` wywoływane przez `call()` (np. `saveDyspozycja`), nigdy `google.script.run`.

## Polecenia

```bash
npm test                         # testy Node (Code.gs w piaskownicy, web/lib.js) + UI w Playwright z atrapą API; zrzuty w tests/screens/
npm run test:code                # tylko logika serwera
node tools/validate-plan.js plans/x.json   # sprawdzenie planu przed wrzuceniem na Drive
node tools/make-icons.js                   # ikony w web/icons/: talerz z nazwą marki na obwodzie (po zmianie podbij VERSION)
npm run serve                    # podgląd web/ na http://localhost:8080 (API z config.js)
npm run gas:push                 # clasp push → Apps Script (pliki z apps-script/)
DEPLOYMENT_ID=… npm run gas:deploy   # nowa wersja istniejącego wdrożenia (URL /exec bez zmian)
git push                         # zmiany w web/ → GitHub Actions → GitHub Pages
```

Każda zmiana w `web/` wymaga podbicia `VERSION` w `web/sw.js`, bo inaczej telefony mogą trzymać starą wersję.
Każda zmiana w `Code.gs` wymaga `gas:push` i `gas:deploy`. Bez deploy telefon dalej rozmawia ze starą wersją API.
Robi to automatycznie `.github/workflows/apps-script.yml` po scaleniu zmian w `apps-script/**` do `main` (testy → `clasp push` → nowa wersja istniejącego wdrożenia). Sekrety repozytorium: `CLASPRC_JSON`, `SCRIPT_ID`, `DEPLOYMENT_ID`. `clasp push` zastępuje cały projekt Apps Script plikami z `apps-script/`, więc poprawki zrobione tylko w edytorze Apps Script przepadną: najpierw przenieś je do repo.

## Dane (arkusz)

**Plan** (PLAN_HEADERS w Code.gs): klient, tydzien, jednostka, tytul, data (RRRR-MM-DD, tekst; opcjonalna = wstępna, klient może przesunąć), nr, cwiczenie, prio (A/B/K), serie, powt (tekst: „8”, „6-8”, „8/str”, „1+1”), procent (ułamek), kg (liczba lub tekst: BW, guma), rpe_max, uwagi, dod_serie, drop, grupa (R/P/CR/CP/PS/I), zamienniki („;”), blok (np. B2), zrodlo (klient = własny trening; dodane / usuniete / usuniete_d = zmiany klienta w jednostce trenera; trener = ćwiczenie albo jednostka dodane w trybie „Prowadź”, liczy się jak plan, w getData `row.coach`), tryb (EMOM), ciecie (1 = tnij pierwsze), serie_min, obwod (litera A–Z: sąsiednie ćwiczenia jednostki na zmianę, min. 2, bez EMOM; `circuit_`, w getData `row.circuit`), uwagi_jedn (notatka trenera do całej jednostki, w jednym wierszu jednostki; dwie różne w jednostce = błąd walidacji; w getData `row.unote`, w aplikacji karta „Od trenera” `#unote` nad kartą „dziś”, `unoteCard`; w trybie skupienia tylko na pierwszym kroku). Serie 1–40 (`SETS_MAX`).
Kolumny E (data), J (powt) i L (kg) muszą mieć format `@` ustawiony PRZED zapisem, bo inaczej Arkusze zamienią „6-8” w datę.
Tygodnie u klienta numeruj **ciągle** między blokami (blok 2 od tyg. 7): id serii nie zawiera bloku, więc powtórzony numer tygodnia nadpisałby Log.

**Klienci**: A klucz, B klient_id, C imie, D aktywny (TAK/NIE), E link, F bol (TAK), G tryb (PROSTY/PRO), H dod_serie, I masters (TAK), J zamiana (NIE / TRENER / DOWOLNA; TAK = TRENER, `swapMode_`), K skala (RPE/RIR), L sufit_oly (ułamek lub %, domyślnie 0,05), M wlasne (NIE wyłącza własne treningi), N edycja (TAK = zmiany w jednostce trenera), O email (tylko do porannego maila), P mail_rano (TAK = poranny mail, `apps-script/Mail.gs`). `getData` zwraca je w `cfg` jako `swap` ('TRENER' | 'DOWOLNA' | false), `scale`, `olyCeil`.

**Log**: id = klient|tydzien|jednostka|nr|seria (upsert), zapisano, klient, tydzien, jednostka, data, nr_cw, cwiczenie, seria, kg, powt, rpe, vbt_ms, wykonane, film_link, uwagi, typ, ocena (L/S/W/X), vbt_peak, wysokosc_cm, sciezka (JSON), zamiana („oryginał → zamiennik | powód”), komentarz_trenera, komentarz_dysk, odpowiedz_klienta, odpowiedz_at, notatka_trenera (prywatna notatka trenera z trybu „Prowadź”, nigdy w `getData` klienta).
Wartości `seria`: 1…n robocze, n+1… dodatkowe, R1… rozgrzewka, D1… drop set, 0 = ćwiczenie pominięte/skrócone. Wartości `typ`: DROP / FAIL / DROP+FAIL / SKIP (seria 0, `wykonane` puste, powód w `uwagi`: „skrócone do 2 z 4 serii · brak czasu” albo sam powód; `skips_`).

**Sesje**: id = klient|tydzien|jednostka, …, samopoczucie (1–5), czas_min, uwagi, start, koniec, bol („miejsce:0–10; …”), bol_max, rpe_sesji (0–10, CR-10), komentarz_trenera, odpowiedz_klienta, odpowiedz_at, prowadzil (trener = jednostkę zapisał trener w trybie „Prowadź”).

Plany tworzy Claude w projekcie claude.ai („Trener personalny (OLY)”) i zapisuje je jako JSON do `Trening – Klienci/_plany/` na Drive.

Kolejno: waliduje plik (`validatePlan_`), podmienia wiersze klientów z pliku (`mergePlan_`: **tylko bloki, które plik zawiera** (`blok`, pusty też jest blokiem) i jednostki z pliku; niezrobione jednostki tych bloków spoza pliku znikają i każda jest w Import „usunięto: klient tydz. X jednostka Y (blok Z)”, status „OK (usunięto N)” (`removed`, `importStatus_`); inne bloki klienta zostają; jednostka zrobiona = wpis w Sesjach **albo** seria robocza / dodatkowa / drop z ✓ lub FAIL w ćwiczeniu A/B (`unitsDone_`, `doneWork_`, `doneKey_`; nie korekcja K, chyba że jednostka ma same K; nie rozgrzewka, pominięcie, wyzerowana seria ani sam film; `wczytajPlany` czyta z Logu `DONE_LOG_COLS` przez `pgTable_`; ta sama reguła w porannym mailu, `trPlanEdit_`, `trMailProba` i w panelu `planUnits` przez lib `doneUnits`, od 23.11) i zawsze zostaje bez zmian; niezrobiona jednostka z zapisaną serią, w której plik ma inne ćwiczenie pod tym numerem = uwaga w Import (seria przypisze się do nowego ćwiczenia), spoza pliku z uwagą; niezrobiona jednostka innego bloku z tym samym tygodniem i dniem co plik = zastąpiona, uwaga; własne (`zrodlo` = klient) nietknięte; zrobiona jednostka z innym blokiem w pliku = błąd; opcjonalne pole wiersza `zastepuje` = blok, którego niezrobione jednostki klienta z datą ≥ pierwszej daty klienta w pliku są zamykane, bez ruszania Logu, Sesji i własnych; w Import „zamknięto n jedn. bloku X”, nieistniejący blok = uwaga; `zastepuje` nie jest kolumną Planu), przenosi plik do `_plany/wczytane` albo `_plany/bledy` i zapisuje wynik w zakładce Import.

## Interfejs (web/index.html)

- `Index.html` jest wspólny dla wszystkich klientów. Różnice między klientami robi się przez `cfg` z getData (pain, simple, extra) albo przez kolumny planu, **nigdy** przez warunki na konkretne imię.
- Tryb prosty (`SIMPLE`):
  - „jak ciężko?”: te same światła co w PRO (Lekko / Średnio / Ciężko / Nieudana), słowem zamiast liczby, bez dokładnego RPE;
  - „✓ Wszystko jak w planie”;
  - podpowiedź RIR;
  - ukryte VBT i %.
- Pola kg / powt.: propozycja (plan, poprzednia seria, drop) to placeholder (`data-ph`, klasa `ph`), pole puste; wartość czytaj przez `fv(input)`, nową propozycję ustawiaj `setPh`. ✓ przy pustym polu wpisuje propozycję. Pole z wartością zaznacza się przy fokusie.
- Serie:
  - dodatkowe przyciski „+ rozgrzewka”, „+ seria (N)” i „+ drop set” (~80% ciężaru, w dół do 2,5 kg; „⇣ Jak 1. seria” usunięte w v4);
  - proponowana rozgrzewka (v74; lib `warmupSets`, `noBar`; `warmPlan`, `warmTxt`, `addWarm`): przy ćwiczeniu A z liczbą kg w planie pasek `.wu` „Rozgrzewka” nad seriami (gryf × 8 / boje × 5, ok. 40 / 60 / 80% × 5 / 3 / 2, przy ≤ 3 powt. i ≥ 100 kg 90% × 1; gryf z `pl_<klucz>`), „Wstaw (n)” (`data-wuadd`) dodaje wiersze R1… z propozycją jako placeholder, „+ rozgrzewka” bierze kolejny krok; pasek schowany po wstawieniu i po zapisanej serii roboczej. `followRow` ignoruje wiersze rozgrzewki (nie zmieniają propozycji serii roboczych);
  - ✕ usuwa ostatni dodany wiersz w dwóch dotknięciach;
  - pole odhaczenia (`data-st`): puste → ✓ zrobiona → ✕ nieudana (typ FAIL, rpe puste) → puste; żółte (`pend`) = czeka w kolejce;
  - dotknięcie numeru serii roboczej/dodatkowej: zwykła → drop (typ DROP) → nieudana;
  - zmiana kg/powt./RPE w zapisanej serii zapisuje ją od razu;

    | Światło | `rpe` w Logu | `typ` | Podpis |
    |---|---|---|---|
    | 🟢 Lekko | 7 | – | Szybko, czysto, zapas ≥ 3 |
    | 🟡 Średnio | 8 | – | Wolniej albo z poprawką, zapas 2 |
    | 🔴 Ciężko | 9 | – | Walka, zapas 0–1 |
    | ✖ Nieudana | puste | FAIL | Seria nie wyszła |

- `npm test` musi przechodzić przed każdym commitem.
- Przy zmianach UI:
  - sprawdź oba tryby (PROSTY i PRO) i oba motywy;
  - przejrzyj zrzuty 390×844 w `tests/screens/` (PROSTY/PRO × jasny/ciemny; tworzy je `npm test`, poza repo);
  - sprawdź payloady wysyłane do API.
- Nie dodawaj zależności do `web/`: wszystko inline, bez CDN, bo aplikacja musi działać offline.
- v2: testy jednostkowe dla `sugOly`, `verdict`, `analyse` i przeliczenia RPE/RIR; Playwright z atrapą `call()`/`fetch`, zrzuty 390×844 w jasnym i ciemnym motywie, tryby PROSTY i PRO, tryb offline.
